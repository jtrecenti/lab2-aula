De tidymodels para scikit-learn

Lab 2: Prática Avançada em Data Science e Visualização, PADS Insper

Julio Trecenti

Vocês já sabem modelar

No R, vocês montaram fluxos assim:

recipe(...) |> step_...() -> workflow() -> tune_grid() -> last_fit()

O scikit-learn faz as mesmas cinco coisas, com outros nomes:

  • dividir dados de um jeito honesto
  • descrever o pré-processamento sem executá-lo
  • descrever o modelo sem executá-lo
  • colar os dois num objeto só
  • reamostrar, ajustar hiperparâmetro e medir

Hoje é tradução, não conteúdo novo. Quem entendeu workflow() já entendeu Pipeline.

O mapa

tidymodels (R) scikit-learn (Python)
rsample sklearn.model_selection
recipes ColumnTransformer + transformadores
parsnip os estimadores (Lasso, RandomForestRegressor, …)
workflows Pipeline
tune GridSearchCV, RandomizedSearchCV
yardstick sklearn.metrics
bundle / vetiver joblib.dump

Diferença de forma: no R são oito pacotes que conversam pelo tidymodels. Em Python é uma biblioteca com submódulos.

O problema de hoje

Quanta oferta de ônibus a SPTrans coloca em cada linha, em cada hora?

Alvo: headway, o intervalo programado entre dois ônibus, em segundos.

  • 37.357 registros
  • 1.142 linhas de ônibus
  • 11 variáveis numéricas, 6 categóricas
  • fonte: GTFS da SPTrans cruzado com a API Olho Vivo
um registro
linha 8000-10
sentido ida
faixa 07h
extensão 14,3 km

corredor não

Tudo o que vem a seguir está nos dois documentos irmãos, tidymodels.qmd e sklearn.qmd: mesmo dado, mesmos modelos, duas sintaxes.

Dois modelos, escolhidos de propósito

Lasso

Regressão linear com penalização L1.

  • precisa de padronização
  • zera coeficiente, então também seleciona variável
  • interpretável
  • um hiperparâmetro: a penalidade

Floresta aleatória

Muitas árvores, cada uma numa amostra.

  • não precisa de padronização
  • captura não linearidade e interação
  • caixa mais fechada
  • sobreajusta com facilidade

Eles cobrem os dois extremos do pré-processamento. Se o seu Pipeline serve para os dois sem mudar a receita, ele está bem construído.

Diferença de filosofia (a que mais confunde)

tidymodels

A receita conhece papéis:

step_dummy(all_nominal_predictors())
step_normalize(all_numeric_predictors())

Você diz o que é a variável.

scikit-learn

O ColumnTransformer conhece colunas:

ColumnTransformer([
  ("num", caminho_num, numericas),
  ("cat", caminho_cat, categoricas),
])

Você diz quais colunas.

Dá para chegar perto do R com make_column_selector:

from sklearn.compose import make_column_selector as selecionar
("num", caminho_num, selecionar(dtype_include="number"))

Na prática, listar as colunas explicitamente é melhor: a lista vira documentação do modelo, e você percebe na hora quando uma coluna nova apareceu.

Passo 1: dividir por grupo

Cada linha de ônibus aparece cerca de 30 vezes, uma por faixa horária. Se a mesma linha cair nos dois lados, o modelo decora a linha.

divisao <- group_initial_split(
  dados,
  group = route_id,
  prop = 0.75
)

treino <- training(divisao)
teste  <- testing(divisao)

dobras <- group_vfold_cv(
  treino, group = route_id, v = 5
)
# train_test_split NAO tem groups=,
# entao sorteamos as LINHAS, nao os registros
linhas = dados["route_id"].unique()
linhas_treino, _ = train_test_split(
    linhas, test_size=0.25, random_state=42
)

e_treino = dados["route_id"].isin(linhas_treino)
treino, teste = dados[e_treino], dados[~e_treino]

GroupKFold(n_splits=5)

A forma canônica seria GroupShuffleSplit, mas ele é um validador cruzado: o .split() devolve um gerador de índices, e é preciso next() para pegar a primeira divisão. Dá exatamente o mesmo resultado; a versão acima é só mais fácil de ler. Na validação cruzada não tem escapatória: ali é GroupKFold.

No R o route_id viaja dentro do data.frame. Em Python o vetor groups viaja por fora, e precisa ser passado em toda chamada. Esquecer o groups= no .fit() da busca é o erro número um.

Passo 2c: três armadilhas da receita

A mesma receita, no mesmo dado, termina com 44 colunas no R e 62 no Python. Duas causas somadas:

  1. step_dummy() cria k menos 1 colunas, deixando um nível de referência; o OneHotEncoder cria as k. Isso explica 6 colunas, uma por variável categórica. Para lasso e floresta muda pouco; para interpretar coeficiente, muda tudo.
  2. A régua para categoria rara é outra. O step_other() corta por proporção (threshold = 0.005, ou seja 139 dos 27.768 registros de treino); o min_frequency corta por contagem (20 registros). O corte do R é sete vezes mais agressivo, e sozinho explica as outras 12 colunas.
  3. Ordem importa no R: step_normalize() tem que vir antes de step_dummy(), senão ele padroniza as dummies. Em Python o problema não existe, porque cada caminho recebe a sua própria lista de colunas.

Aviso

E a regra que vale nas duas: fit e prep só no treino. Rodar fit_transform na base inteira antes de dividir é o vazamento mais comum de todos.

mixture = 1 é lasso, 0 é ridge, entre 0 e 1 é elastic net.

Passo 4: workflow = Pipeline

fluxo_lasso <- workflow() |>
  add_recipe(receita) |>
  add_model(especificacao_lasso)
fluxo_lasso = Pipeline([
    ("receita", receita),
    ("modelo", modelo_lasso),
])

É por isso que este slide existe

O Pipeline não é açúcar sintático. Ele é o que garante que a receita seja reajustada dentro de cada dobra da validação cruzada, e o que faz o modelo salvo receber dado cru em produção.

Passo 5: ajustar a penalidade

grade <- tibble(
  penalty = c(0.1, 1, 10, 100)
)

resultado <- tune_grid(
  fluxo_lasso,
  resamples = dobras,
  grid = grade,
  metrics = metric_set(mae, rmse, rsq_trad)
)

melhor <- select_best(
  resultado, metric = "mae"
)
busca_lasso = GridSearchCV(
    fluxo_lasso,
    param_grid={
      "modelo__alpha": [0.1, 1.0, 10.0, 100.0]
    },
    cv=GroupKFold(n_splits=5),
    scoring="neg_mean_absolute_error",
    n_jobs=-1,
)
busca_lasso.fit(
    X_treino, y_treino, groups=g_treino
)
busca_lasso.best_params_

O __ é o operador de caminho: "modelo__alpha" significa o parâmetro alpha do passo chamado modelo. No R o buraco é marcado por dentro, com tune(); em Python ele é apontado de fora, pelo nome.

Passo 5b: o __ alcança a receita também

grade = {
    "receita__num__imputar__strategy": ["median", "mean"],
    "receita__cat__onehot__min_frequency": [10, 50],
    "modelo__alpha": [0.1, 1.0, 10.0],
}

Isso ajusta receita e modelo juntos, na mesma validação cruzada. No tidymodels é o tune() dentro do step_*:

step_other(all_nominal_predictors(), threshold = tune())

Mesma ideia, sintaxe diferente. E cuidado com o tamanho: cada camada multiplica o número de ajustes.

O que o lasso escolheu

Com penalty = 1 no R, os coeficientes de maior módulo:

variável coeficiente (segundos)
periodo_dia_madrugada +933
area_operacao_M (metrô) -932
tipo_dia_util_e_sabado +737
n_paradas +343

Leitura direta: madrugada tem intervalo muito maior; linhas de metrô e trem têm intervalo muito menor; linha mais longa tem intervalo maior.

E 2 dos 44 coeficientes foram zerados no R (21 de 62 no Python, porque a régua da penalidade não é a mesma nas duas implementações). O lasso é regressão e seleção de variável no mesmo passo.

Passo 6: a floresta, trocando uma linha

especificacao_floresta <- rand_forest(

grade = {"modelo__min_samples_leaf": [5, 20]}

min_n é min_samples_leaf; trees é n_estimators.

A receita não mudou. Trocar de modelo custou uma linha nos dois lados. É esse desacoplamento que o Pipeline compra.

Passo 7: o resultado, nos dois

Métricas no teste, em linhas que o modelo nunca viu:

modelo MAE (R) MAE (Python) R² (R) R² (Python)
baseline (mediana) 690 s 667 s -0,26 -0,22
lasso 589 s 594 s 0,28 0,25
floresta 574 s 562 s 0,31 0,27

Nota

Os números não batem na casa decimal porque os geradores de números aleatórios de R e Python são diferentes, então a divisão treino e teste não é exatamente a mesma. A ordem de grandeza e a conclusão são.

Como ler essa tabela

  1. Os dois modelos ganham do baseline, mas por pouco: cerca de dois minutos de erro médio. O gargalo não é o algoritmo, são os dados.
  2. A floresta ganha do lasso por pouco no teste, e por muito no treino (R² 0,79 contra 0,32). Essa distância é sobreajuste.
  3. O R² do baseline é negativo. O R² compara com prever a média, e o baseline prevê a mediana, que é o chute constante certo sob MAE. Métrica e baseline precisam ser escolhidos juntos.
  4. R² de 0,30 é o achado, não o fracasso: a estrutura física da linha explica pouco da oferta. Falta demanda, falta contrato de operação. O modelo diz quais dados faltam.

Cuidado com o R²

Importante

yardstick::rsq() é o quadrado da correlação entre observado e predito. Com um baseline constante, a correlação não existe e ele devolve NA.

sklearn.metrics.r2_score é 1 - SQE/SQT, que pode ficar negativo.

O equivalente exato em R é o yardstick::rsq_trad().

Se você comparar um relatório em R e um em Python e os R² não baterem, olhe aqui primeiro.

Pegadinha irmã, do lado do Python: dentro do GridSearchCV, scoring é sempre “quanto maior, melhor”. Por isso existe neg_mean_absolute_error, e por isso o best_score_ vem negativo.

Onde o scikit-learn não segura sua mão

  • Não existe fórmula. Não há headway_seg ~ .; você separa X e y na mão.
  • Não existe update_role(). Coluna que não é preditor simplesmente não entra em X.
  • Nomes de coluna somem. A saída padrão é um array numpy. Use set_config(transform_output="pandas") ou .get_feature_names_out().
  • Tipo não vem de graça. Ler CSV devolve "10" e 10 misturados e o OneHotEncoder recusa. No R, factor resolve.
  • Nada estratifica nem agrupa sozinho. stratify= e groups= precisam ser passados em todo lugar, sempre.

O teste que importa

Se o objeto salvo não aceita um DataFrame cru, é porque alguma transformação ficou fora do Pipeline. Isso vira bug no dia do deploy, não hoje.

O que fica

  1. Pipeline é workflow. Se o pré-processamento não está lá dentro, ele vai vazar em algum momento.
  2. A mesma receita serviu ao lasso e à floresta. Se a sua não serve, ela está grudada no modelo.
  3. A validação tem que imitar o uso. Se o modelo vai ver linha nova, o teste precisa ter linha nova: por isso GroupKFold.
  4. Baseline sempre. Uma linha de código evita comemorar um R² que não significa nada.
  5. O objeto salvo é o produto. Ele recebe dado cru e devolve predição. Esse é o contrato com a disciplina de Deploy.
